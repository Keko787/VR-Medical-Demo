VisBox CAVE · MiddleVR 2.4.0.4 · investigation report

The wand isn't lagging. The frame is.

VR-Demo and Sit-Rep looked laggy next to the CAVEWeather app because they were being run from the Unity Editor, which lands on the wrong GPU and renders the CAVE at 14 FPS. The Weather build is fast only because MiddleVR's player wrapper moves it to the GPU that drives the walls. Same exe, swapped GPU: 52.6 → 14.0 FPS.

19.1 ms per frame. MiddleVR's wrapper respawned it with -force-device-index 1: Unity and the compositor on the RTX A6000, presenting on the GPU that owns the walls.

Motion-to-photon for anything parented to HandNode is roughly two to three frame periods (the frame it was sampled in, up to two queued frames, then the compositor's own present). At 72 ms a frame that is 150–250 ms of pose age — "hard to aim". At 19 ms it is 40–60 ms, which by hand reads as "follows the wand". Nothing about the gun, the tracer or the pointer scripts differs between the apps in a way that costs a single frame.

What was actually being comparedEditor sessions against a wrapped build

Every MiddleVR kernel log that survives for VR-Demo and Sit-Rep begins with Executable path: …\Unity.exe and -projectpath. Neither project has a usable build on disk: VR-Demo\Build and Sit-Rep-CAVE\Build date from June/July, contain only Boot.unity, and still carry xrsdk-pre-init-library=UnityOpenXR in boot.config. The shooting gallery and physics scenes have only ever run in Play mode.

The Weather app, by contrast, is a Unity 2021.2.19f1 standalone build launched by RUN_CAVEWeather_HDRP.bat. Its CaveWeather_HDRP.exe is byte-identical (MD5) to MiddleVR's MiddleVR_UnityPlayer.exe — the wrapper MiddleVR's post-build step installs in place of the real player. Given --config, that wrapper loads the .vrx, finds the DXGI adapter whose output contains the window, and relaunches the game on it.

So the question "why does project A lag and project B not" was really "why does the Editor lag and a wrapped Player not".

Where the frame goesTwo GPUs, and the walls hang off the second one

The kernel's own timing makes the placement the prime suspect before any test: the Editor frame period is content-independent (a 126-rigidbody physics scene, a near-empty gallery and an unrelated football project all sit at 13–15 FPS), and the occasional 5–9 ms kernel delta shows the CPU side of a whole frame is cheap — the other ~60 ms is spent waiting on the present path.

The decisive testSame app, same scene, same config — only the GPU changed

The Weather build makes its own control: appending --start-unity-process (the flag the wrapper normally hands its child) tells the stub to run Unity in-process, which skips the respawn and leaves the game on the default adapter — exactly the placement the Editor gets. And the Editor can be fixed the same wayThe Windows Editor honours the flag

Unity's documentation lists -force-device-index for the Editor as macOS-only. It works on the Windows 2022.3 Editor: launching Unity.exe -force-device-index 1 -projectPath …\VR-Demo produced an Editor whose only 3D-engine instance is on LUID 0x2618f.

// Editor.log, 2026-09-14 10:27
COMMAND LINE ARGUMENTS: Unity.exe -force-device-index 1 -projectPath …
GfxDevice: creating device client; threaded=1; jobified=0
    Renderer: NVIDIA RTX A6000 (ID=0x2230)      ← every earlier session: NVIDIA Quadro RTX 4000

The compositor takes Unity's adapter, so a Play-mode run from that Editor should log Using Adapter 'NVIDIA RTX A6000' and a frame rate in the Weather build's range rather than 14. That number is the one measurement still open.

Ruled out along the wayThings that looked like causes and weren't

  • The pointer code pathMVRNodesMapper writes HandNode straight from the kernel matrix at execution order −100, no smoothing (HandNode IsFiltered=0 in both configs). The gun is a plain child via a one-shot MVRAttachToNode; GunController.Update raycasts and Tracer.LateUpdate draws from the same frame's muzzle. The Weather laser is MiddleVR's stock MVRWandRay on the same HandNode — identical sample point, zero extra frames.
  • Scene, physics, scripts126 rigidbodies + 117 joints (Physics scene) and 0 rigidbodies (gallery) give the same 14 FPS; project scripts do a raycast, two LineRenderer.SetPosition calls and a few P/Invoke button reads per frame. Solar-System-CAVE, with none of this code, hits the same ceiling.
  • URP quality, MSAA, HDRWith a compositor render texture, URP takes msaaSamples from targetTexture.antiAliasing, which MiddleVR sets to 1 — the asset's MSAA 4× never applies. Per-camera GPU work for the 8 views is a few milliseconds on either card.
  • The Weather .bat flags--mvr-window-geometry is a MiddleVR 1.x option; no 2.4 binary contains the string, and the log shows the full 2560×6400 four-wall window. -popupwindow shapes a window MiddleVR hides; -force-d3d11 picks the API the Editor already uses.
  • MiddleVR itself, tracking, licenceMiddleVR2.dll, MiddleVR_UnityRendering.dll, MiddleVR_Compositor.exe and the DTrack driver are MD5-identical between the Weather build and the package the projects use; same visbox MVR.vrx; licence checked out once at start.
  • Per-frame loggingThe lagging projects log nothing per frame (47 Editor.log lines in a 7 500-frame session). The Weather build throws four NullReferenceExceptions and prints a collider name every frame — and is the smooth one.
  • Script execution orderMiddleVR's manager runs at −100, project scripts at 0, so poses are fresh. Only one-frame nits remain (the tracer dot is placed in Update; Sit-Rep's beam is still drawn in Update; Sit-Rep's WandOperatorInput samples at −1000) — each worth ~70 ms at 14 FPS, ~19 ms at 52.
  • Editor throttling, Game-view freezePlay mode ignores Interaction Mode; Game-view VSync off; the 60-frame log cadence never stalls, so WaitForEndOfFrame (which drives the compositor present) was firing every frame.

What to doFix, in the order it pays off

  1. Judge latency from a wrapped build, never from Play mode. Rebuild VR-Demo with the demo scenes enabled and launch it the way Weather is launched — the wrapper places it on the A6000 by itself: 
    "C:\Users\Exx\KostageProjects\VR-Demo\Build\VR Demo.exe" --config "C:\Users\Exx\Desktop\visbox\config\MiddleVR\MVR.vrx" -popupwindow -force-d3d11
    Confirm in %LOCALAPPDATA%\Temp\MiddleVR\MiddleVR_<date>\Unity_Player.txt that Renderer: says A6000. Standalone default quality is level 5 "Ultra" (HDR on, per-pixel lights) while the Editor runs "Low" — set them equal before comparing numbers.
  2. For Editor sessions in the CAVE, add -force-device-index 1. Unity Hub → project ⋮ → Add command line arguments, or launch Unity.exe directly. Verify with Editor.log's Renderer: line and the compositor's Using Adapter line. (Making the mosaic the Windows main display achieves the same thing without the flag.)
  3. Then trim pipeline depth. QualitySettings.maxQueuedFrames = 1 removes one queued frame of pose age; move the tracer dot into LateUpdate beside the beam; port VR-Demo's LateUpdate Tracer to Sit-Rep; sample Sit-Rep wand buttons after order −100.
  4. Longer term. MiddleVR 2.4.0 does not support Unity 2022.3 (its version guard is commented out; 2022.3 support arrived in 2.5.9), and its built-in FPS overlay throws on 2022.3 (Arial.ttf). MiddleVR 3 is already installed at C:\Program Files\MiddleVR3.
The Weather app is not lag-free in absolute terms either: 19 ms frames through a two-to-three-frame pipeline is still 40–60 ms of pose age. It is simply below what a hand notices. A 120 Hz mosaic could be driven at 8 ms frames once the placement is right and the 8-view render is trimmed.
